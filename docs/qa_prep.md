## 一、架构与选型（4 题）

### Q1：为什么用 LangGraph 而不是直接用 LangChain 写一条链？

A：核心原因是「规划-检索-批评-生成」四步之间需要反复迭代——比如 Critic 发现答案缺依据就回退到 Planner 重规划，简单的链式编排很难表达这种循环控制流。LangGraph 用 StateGraph 把节点和条件边显式画出来，最大迭代次数封顶 3 次（避免死循环），配合 PostgreSQL checkpoint 还能跨请求持久化对话状态。直接用 LangChain 的话，要么得自己写循环、要么得塞一堆 if-else，结构上比 LangGraph 难维护。LangChain 反而是组成 LangGraph 节点的工具之一，并不是替代关系。

### Q2：Hybrid 检索为什么选 BM25 + 向量 + Reranker，而不是单一的向量检索？

A：单一向量检索有两个明显的短板：一个是精确词 / 代号 / 缩写容易召回失败（embedding 没有「玄铁-9」这种代号的概念），另一个是对低频专有词不友好。我们的 110 条评测里专门设计了「同义改写」和「跨语言」两类样本，单一向量在这两类上 top-1 命中率就掉下去了（具体看报告 §7.2 汇总表）。BM25 走 BM25 打分处理字面精确匹配，向量走 HNSW 处理语义泛化，两者 RRF 融合后 top-5 召回率从 83.64% 提到 89.09%，最后 Reranker 再把 top-1 精度从 69.09% 拉到 74.55%——三个环节各司其职，是有数据支撑的工程取舍。

### Q3：Reranker 为什么用 BGE 而不是其他重排模型？

A：BGE-Reranker 是中文社区重排事实标准，bge-reranker-base 在 HuggingFace 上有官方维护的中文训练集，跨领域泛化在公开榜单上排到第一梯队；另一个备选 Cohere Rerank 是闭源 API，受限于网络和成本。结合本项目完全本地化的部署目标，bge-reranker-base 走 sentence-transformers 加载、CPU 推理即可用，性价比最高。代价是延迟——CPU 单次精排约 1.49 秒，这也是报告里 Reranker 超时降级那条 limitation 想解决的问题。

### Q4：为什么不直接调 ChatGPT 或 GPTs 做 RAG？

A：主要是数据合规和成本两点。我们做的是企业内网场景，原始合同、手册、HR 制度都在私有库里，不能把向量化的明文传给公网模型。本项目把 LLM 换成 DeepSeek、把 Embedding 换成 BGE 都跑本地 / 内网，pgvector 也是自建，整个链路没任何数据出境。另一个是单价：演示场景一次检索走 Reranker 要打分 20 条 × 1024 维 embedding + 重排，单条成本对日常使用偏高；本地推理边际成本接近 0。所以选型时本地化优先，RAG 架构本身各家通用。

## 二、检索策略（3 题）

### Q5：RRF 是什么？为什么不用加权打分融合？

A：RRF 全称 Reciprocal Rank Fusion，按各路排名倒数加和：排名第 r 位贡献 1/(k + r)，常数 k 取 60。这样做的好处是不需要把 BM25 原始分数和向量余弦相似度强行做线性加权——这两种分数的数值范围和分布完全不同，硬加权对权重超敏感（设成 0.3 还是 0.4 整条曲线都抖），RRF 只用排名信息反而更稳。代价是丢了绝对分数信息，但下游 Reranker 会再算新分数，所以可以接受。报告 §4.3 给了完整公式推导。

### Q6：查询改写到底提了多少提升？怎么测的？

A：在完整管线（BM25+向量+Reranker）的 110 条评测集上，开启查询改写后：top-1 命中率从 74.55% 涨到 80.00%（+5.45 个百分点），MRR 从 0.7889 涨到 0.8321（+5.49pp），nDCG@5 从 0.8026 涨到 0.8446（+5.23pp）。这个提升主要来自「复杂查询子集」（多主题干扰 / 跨语言 / 反向否定 66 条），top-1 从 62.12% 涨到 71.21%，体现改写对「一句话塞多约束」的拆解能力。HyDE 在我这套数据上没明显提升（top-1 持平），原因写在报告 §8.1 第 4 条 limitation 里，主要假设文档向量和真实答案分布在反向否定场景下会偏。

### Q7：HNSW 为什么能比暴力检索快这么多？

A：HNSW 全称 Hierarchical Navigable Small World，本质是把向量空间组织成多层「邻近图」：顶层图稀疏做跨簇跳转，越往下图越稠密做精细定位。检索时从顶层入口点贪心游走到最近邻，再下钻一层，循环到最底层。复杂度近似 O(log N) 而暴力的 O(N)，并且对低维（512-1024 维）近似率非常高。我们用 pgvector 的 `hnsw + vector_cosine_ops` 索引，单库 22 万向量（1 万 chunks × 1024 维）下 P50 仍能压在毫秒级。具体数据在报告 §7.3 性能基准里。

## 三、重排与降级（2 题）

### Q8：Reranker 1300 多毫秒太慢，演示时怎么办？

A：这就接上了报告 §8.2 第 2 条 limitation——我们做了三件事：第一，加 `rerank_top_k=30` 截断，送精排的候选最多 30 条，超出按粗排分数截掉；第二，`asyncio.wait_for(rerank_timeout=1.5s)` 硬超时，超时自动降级到 RRF 粗排（不是中断请求，是回退到无 Reranker 的排序结果），P99 长尾从 3.13s 压到 1.63s；第三，跑 benchmark 对比 Reranker OFF（51.36ms P50）vs ON（1486.59ms P50），把「性能与精度的取舍」显式量化出来。线上生产用 Reranker OFF 优先，演示场景看哪个效果更好就开哪个，这是配置一行的事。

### Q9：超时降级后用户感知得到吗？

A：体感上没区别。因为降级策略只在 wait_for 触发时生效：超时设置 1.5 秒，1.5 秒对前端 SSE 流式输出本来就在心里预期内；降级后只是少了一次精排，结果仍是粗排 top-10，质量损失肉眼几乎无感。我们还加了告警日志（`logger.warning("Reranker 超时...")`），线上这种日志积累多了就触发 P2 告警，提醒运维查 GPU/IO 抖动。

## 四、评估体系（2 题）

### Q10：RAGAS 怎么评的？四个指标各代表什么？

A：RAGAS 是开源的 RAG 评估框架，思路是「LLM-as-judge」。我用其四个核心指标在 44 条样本上跑了评测：

- **faithfulness = 0.6924**：回答是否忠于检索上下文（无幻觉编造）
- **answer_relevancy = 0.6156**：回答与问题的相关程度
- **context_precision = 0.7853**：相关上下文在检索结果中的排序精度（5 条里前几条命中）
- **context_recall = 0.8409**：检索结果覆盖参考答案信息的比例

context_recall 0.84 说明检索召回没问题，faithfulness 0.69 是接下来要重点攻的点。报告 §7.4 表 7-X 列了完整数据。faithfulness 偏低主要来自反向否定类问题——大模型容易被「不是 X 吗」反问句式带偏，需要在 prompt 模板里加显式声明，详见报告 §8.1 第 1 条。

### Q11：110 条评测集是怎么设计的？会不会过拟合？

A：评测集按 5 类各 22 条设计，每条对应一个事实陈述：基线直配、同义改写、跨语言（中英互译）、多主题干扰、反向否定（「不是 X 吗」反问）。事实陈述从 22 个合成企业文档里抽，覆盖人事制度、报销、数仓规范、安全合规、生产告警等 8 个业务领域，避免单一领域偏见。110 条里只有 22 条是「基线直配」（直接抄原文），剩下 88 条都是变形题，能一定程度防止「模型死记硬背原文答案」。演示现场会展示 1 类样本的具体问答。

## 五、工程化（2 题）

### Q12：BM25 索引重启怎么处理的？报告里 limitation 怎么解决的？

A：这一点是 Day 9 这次重点改的。原来的 limitation 是 BM25 倒排索引完全在内存里，应用重启后要从 PostgreSQL 拉全部 chunks 重新构建，实测 402 chunks 重建要 1.8 秒。改完的方案是把倒排索引的快照（postings + chunk_freqs + doc_lengths + doc_freq + chunk_ids）以 JSONB 形式落进 PostgreSQL `bm25_index_state` 单行表，启动时优先反序列化快照（实测 25ms），加载失败（schema 不兼容 / 与 chunks 表脱钩）才回退全量重建。增量新增 / 删除 chunk 各自触发一次 save，整体启动加速 ~70 倍。

### Q13：这套系统的并发支撑能力怎么样？

A：实测在 8 并发下能到 3.51 qps（同机 CPU + Reranker ON，CrossEncoder 经线程池并行），瓶颈不在框架而在 CrossEncoder 的 CPU 推理。生产侧有两个缓解方向：一是把 Reranker 模型搬到 GPU（预计单条从 1.4s 降到 200ms，8 并发 ~3-4 qps）；二是把无状态服务拆出来多副本横向扩。架构上 FastAPI async 是天然支持并发的，PostgreSQL 连接池池大小 10 + 溢出 20 能兜住演示 / 小规模生产。报告 §7.3 表 7-V 列了 1/4/8 并发的实测数据。

## 六、部署与运维（2 题）

### Q14：怎么部署？需要什么环境？

A：完整部署分三块：PostgreSQL + pgvector 扩展（向量存储）、Redis（缓存 + LangGraph checkpoint 可选）、Python 后端（BGE-large-zh-v1.5 + bge-reranker-base + DeepSeek API）。演示环境用 Docker Compose 一键起，详见 `docs/deploy.md`；生产部署把 PostgreSQL 托管（RDS / 自建主从）、Redis 拆分、后端多副本 + Nginx 负载均衡，10-20 万文档规模单机 8 核 16G 起步。模型权重 BGE 走 HuggingFace，国内可换到 ModelScope 镜像。整套部署命令、时间、验证步骤都在 `docs/deploy.md` 第 4 节「演示环境」里。

### Q15：如果 DeepSeek API 挂了怎么办？

A：LLM 调用是异步 + 超时重试 + 熔断三件套。请求层面设 30s 超时 + 指数退避 3 次；服务层面用 tenacity 做滑动窗口熔断（5 分钟内失败率超 50% 触发熔断，30s 半开恢复）。熔断触发时接口降级返回一个固定提示：「当前查询队列繁忙，请稍后再试」。同时把失败 query 记到 query_logs 表，运维能立刻拉出最近错误样本来排查。如果做更深一层的灾备，可以把 LLM 换成多模型路由（主用 DeepSeek，备自建 Qwen），但那是 v2.0 范畴。

## 七、演示现场（必读）

### Q16：演示能操作一下吗？

A：可以，演示时长约 6 分 30 秒，共 7 段，全程按 `docs/demo_script.md` 走：登录 → 上传样例 PDF → 提问「青鸾-7 引擎负责什么」→ 切到「年假怎么算」 → 打开 SSE 流式 → 看 dashboard 看板 → 多轮追问。操作前会事先检查清单（4 项：PDF 在桌面、后端正常、模型已加载、合成数据已入库），演示结束问老师是否还有其他想看的。整个流程都用真实合成数据，不是 mock。

### Q17：这套系统和市面上的 Coze / Dify 有什么本质区别？

A：Coze / Dify 是低代码编排平台，适合非技术人员搭 Demo；我们这套是工程化深度优化：BM25 自己用 jieba 切 + 倒排索引实现（对比开源 rank_bm25 词汇表精简 34%），检索融合走 RRF，重排做了超时降级和 top_k 截断，评测用 RAGAS 跑了 110 条 + 44 条两套，并发 1-8 做了 benchmark。简单说，他们解决「让更多人能搭 RAG」，我们解决「搭出来能不能在真实场景跑稳」，定位不同。
